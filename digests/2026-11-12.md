## 一句话摘要

AWS 于 11 月 11 日正式推出免费的本地模拟器 AWS Emulator：开发者和编码智能体可在本机用同一套 AWS API、SDK 与 CLI 做测试，无需账号或云端部署。官方称全部代码由数千个自主智能体编写，人类团队未手写或审阅代码，质量依赖对照真实云的保真度测试，以及由其他智能体执行的安全与回归门禁。

## 深挖

### 背景

在官方模拟器出现之前，要在本地测一段会调 DynamoDB、S3 或 SQS 的代码，常见选择是手写 mock、使用第三方模拟器，或直接打到开发账号里。前两种快，但容易和真实 AWS 的错误码、状态变化对不上；后一种准，却慢、有费用，也不适合让编码智能体在循环里反复创建和销毁资源。

11 月 11 日，AWS 把这条缺口收成正式产品。AWS News Blog 介绍，AWS Emulator 用 Rust 实现，在本机提供 HTTPS 端点（默认 `127.0.0.1:9297`），AWS CLI、各语言 SDK 和编码智能体走同一套云上 API。启动后它会自行生成凭证、配置和证书，访问密钥 ID 以 `EMULATOR` 开头，并拒绝用其他密钥签名的请求；资源状态保存在内存里，进程退出即消失。每个实例有自己的端口、密钥和状态，测试套件、CI 作业和多个智能体互不干扰。Linux 可装 RPM 或 Debian 包，macOS 与 Windows 需按文档用 Docker 运行。产品没有额外服务费，只有部署到真实 AWS 时才计费。源码以 CC0 1.0 公共领域方式发布到 GitHub（`vendor/` 目录除外）。

更引人注目的是它怎么被写出来的。AWS 高级首席工程师 Matthew Goldberg 在官方新闻稿里写道：数千个自主智能体编写了 AWS Emulator 的每一行代码，「我们的团队没有编写或审阅任何代码」。灵感来自今年早些时候 Anthropic 展示智能体可自主完成 C 编译器的实验——前提是既有清晰规格，又有可对照的参考实现。AWS 两边都有：公开的 AWS API Models 是规格，真实云是参考实现。Goldberg 先用很短的提示让 Kiro 按 CLI 写测试、在真云上跑通，再做能通过同一批测试的内存实现；15 分钟后得到一个尚可的 Amazon SQS 雏形，周末又让它补出「其余的 AWS」，缺口不少，但已够团队周一拿来测自己的软件。

做成可交付的产品，靠的是他把智能体分成三组：一组从公开 API 模型设计场景、先在真云上验证，再积累保真度测试（官方称已有数万条，并持续增加）；一组对照模拟器找分歧并提单；第三组每次只修一个问题，必须通过编译、编码规范、安全审查和保真度回归门禁，才能合入。AWS News Blog 补充，这些智能体跑在 Amazon Bedrock AgentCore Runtime 上，经 CodePipeline 与 CodeCommit 发布；安全审查也由独立的安全智能体在修改过程和发布流水线里对抗性完成。仓库不接受外部 PR，GitHub 上能看到他们留下的问题目录：已修好的在 `issues/things-that-now-work/`，仍未通过的在 `issues/things-that-do-not-work/`。

### 为什么重要

这件事有两层意义，而且最好分开看。

第一层是开发工具。编码智能体正在把「写云应用」变成高频试错：建表、写入、读回、改代码、再试一遍。若每次都要等区域部署，反馈太慢，错误会在假设上继续叠代码。AWS 技术思想博客里，Matt Wood 把这一点写得很直白：mock 只能复现你预先想到的响应；模拟器则按当前状态评估请求，智能体才能撞上真实的失败路径——比如 SQS 标准队列里同一订单到达两次、条件写入被拒之后，工作者是否错误地把它当成暂时失败、任由可见性超时后再投递。官方还说，模拟器覆盖「数百个」AWS 服务接口（Goldberg 提到最初生成的是可接收 438 个 API 模型请求、但什么也不做的空服务器），并按服务公布保真度分数（例如「50 项里通过 40 项」）；未实现的操作返回 HTTP 501，以免测试被静默放行。测试套件本身也公开在 `aws-emulator-evaluation-suite` 仓库。

第二层是软件生产本身。一个超大规模云厂商公开把面向客户的开发者工具，交给「人类不写代码、也不做代码审阅」的智能体流水线，并把护栏押在规格、参考实现和合并门禁上。如果这条流水线能跟着 API 模型持续更新、且保真度可信，它不只是 LocalStack 这类第三方工具的官方替代，更是一次可被观察的实验：智能体能否长期维护一张不断膨胀的 API 平面。若不能，最大的风险并不只是开发者本地测不准，而是 Wood 明确警告的那种：用有偏差的环境训练或评估智能体，会强化错误行为——模拟器接受了 AWS 会拒绝的操作，智能体就会把捷径当成正确做法。

### 影响

对开发者和平台工程：本地和 CI 里多了一条「不用账号、毫秒级返回」的 AWS 测试路径，编码智能体（官方点名了 Kiro、Claude Code）可以把云交互的内循环留在笔记本上。对测试可靠性：这只有在你所用的服务、操作恰好落在已通过的保真度测试里时才成立；跨账户、跨区域行为不被支持，IAM 与基于资源的策略也不会按 AWS 的方式评估——官方写明，真实云会拒绝的请求，在模拟器里可能成功，因此不能用它来验证应用是否安全，安全配置和完整应用仍须在 AWS 上测过再上生产。对 AWS 自身：把官方模拟器做成智能体默认的本地闭环，有助于把「先在本机、再用同一套 API 上云」变成更顺的路径。对第三方本地模拟生态：官方、免费、且从第一方 API 模型生成，会改变「谁来定义何谓本地 AWS」的话语权，但短期替代程度仍取决于各服务的保真度分数，而不是发布会表述。另外，默认会向 AWS 发送匿名用量与错误数据，可在启动时关闭；源码构建成本不低，仓库说明完整调试构建的 `target/` 可能需要约 100 GB 磁盘。

### 待观察点

1）各服务保真度分数随版本如何变化，尤其是 DynamoDB、S3、SQS、Lambda 等智能体最常碰到的路径，分数是在提高，还是因测试集扩大而看起来下降；2）IAM、资源策略和多账户场景若长期缺位，生产前「最后一公里」测试会不会仍必须回到真云；3）Goldberg 预告还将公开多智能体工作流、保真度度量与质量安全标准的后续文章，这些细节能否被外部独立复核；4）默认开启的遥测，会不会影响企业在 CI 中的采用；5）第三方模拟器与测试框架是选择兼容、迁移，还是继续在官方覆盖不足的服务上补位。

## 我的看法

AWS Emulator 真正值得盯的，不是又多了一个本地 DynamoDB，而是 AWS 愿意用自己的开发者工具，公开承认「代码可以全部由智能体生产，人类只负责画格子」。这个判断依赖两个前提：对照真云的保真度测试足够密、足够可复现；以及合并门禁——尤其是安全审查——不会随着「每天修复数千个问题、数百个智能体并发改同一仓库」而松掉。若这两个前提成立，智能体写云应用的内循环会明显加快，AWS 也会把「本地默认环境」握在自己手里。若前提不成立，开发者和智能体都会在一个看起来很像 AWS、关键处却不像的环境里积累错误信心。在保真度报告被更多第三方复现之前，我会把它当成强大的本地反馈层，而不是可以省掉预发环境的替代品。
